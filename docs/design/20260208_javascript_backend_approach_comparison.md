## ドキュメント情報

- **目的**: v1とv2のアプローチを比較し、v2採用の根拠を示す

## アプローチの概要

### v1: 2層テスト戦略アプローチ

**基本方針**: Docker依存テストはNative専用、ユニットテストのみJavaScript対応

```
┌────────────────────────────────────────────┐
│  統合テスト (Native専用)                   │
│  - Docker CLI実行 (@process使用)          │
│  - 既存テストを維持                        │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  ユニットテスト (両バックエンド対応)       │
│  - ビジネスロジック                        │
│  - パーサー・バリデーション                │
│  - 新規作成が必要                          │
└────────────────────────────────────────────┘
```

### v2: FFIアプローチ

**基本方針**: JavaScript FFIを使用してDocker CLI実行を実装、統合テストを両バックエンドで実行

```
┌────────────────────────────────────────────┐
│  統合テスト (両バックエンド対応)           │
│  - Native: @process経由                    │
│  - JavaScript: FFI経由 (Node.js)           │
│  - 既存テストをそのまま使用                │
└────────────────────────────────────────────┘
          ↓ Configuration Attribute
┌─────────────────┬──────────────────────────┐
│ docker_native   │ docker_js                │
│ #cfg(native)    │ #cfg(js)                 │
└─────────────────┴──────────────────────────┘
```

## 技術的根拠

### 1. moonbitlang/asyncの実績

moonbitlang/asyncライブラリで同様のアプローチを使用:

```moonbit
// integration.mbt
#cfg(target="native")
pub fn run_async_main(main : async () -> Unit) -> Unit {
  @event_loop.with_event_loop(() => main()) catch { ... }
}

#cfg(target="js")
pub fn run_async_main(main : async () -> Unit) -> Unit {
  let _ = @coroutine.spawn(main)
  @event_loop.reschedule()
}
```

**教訓**: Configuration Attributeで実装を分離するパターンは実績がある

### 2. JavaScript FFIの実績

moonbitlang/asyncでJavaScript FFIを使用:

```moonbit
extern "js" fn set_timeout(duration : Int, f : () -> Unit) -> Timer =
  #| (duration, f) => setTimeout(f, duration)
```

**教訓**: Node.js標準モジュールの使用は安全で効果的

### 3. child_processの安定性

Node.jsの`child_process.execSync`は:
- 標準モジュール（追加インストール不要）
- 安定したAPI
- 広く使用されている
- Docker CLIとの相性が良い

## 推奨事項

### 採用: v2（FFIアプローチ）

**理由**:
1. **完全な機能カバレッジ**: 統合テストが両バックエンドで実行可能
2. **工数削減**: v1より30-40%少ない
3. **既存テスト維持**: 新規テスト作成が不要
4. **高い保守性**: Configuration Attributeで明確に分離
5. **実績あり**: moonbitlang/asyncで同様のパターンを使用

**トレードオフ**:
- Node.js環境が必須（許容可能）
- 若干の実装複雑性（Configuration Attributeで管理可能）
- パフォーマンスがNativeより遅い（1.2-1.5倍は許容範囲）
