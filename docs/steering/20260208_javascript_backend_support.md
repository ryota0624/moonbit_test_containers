# Steering: JavaScriptバックエンドでのテスト実行サポート

## 目的・背景

現在、moonbit_test_containersプロジェクトのテストは`moon test --native`コマンドでのみ実行可能です。MoonBitはマルチバックエンド対応言語であり、JavaScript（Wasm-GC）バックエンドでもテストを実行できるようにすることで、以下のメリットがあります:

1. **クロスプラットフォームでのテスト実行**: ブラウザやNode.js環境でのテスト実行が可能になる
2. **CI/CD環境の柔軟性向上**: Docker環境がない場所でも一部のテストが実行可能になる
3. **開発者体験の向上**: 異なる環境でのテスト実行により、早期に問題を発見できる
4. **バックエンド間の互換性検証**: Native実装とJS実装の挙動の一致を確認できる

## ゴール

以下の状態を達成する:

1. **JavaScriptバックエンドでテストが実行可能**
   - `moon test --target js`または類似のコマンドでテストが実行できる
   - 既存のテストケースがJavaScriptバックエンドで動作する

2. **適切なテストの分離**
   - Docker依存のテストとJavaScript実行可能なテストが適切に分離されている
   - バックエンド固有の制約が明確に文書化されている

3. **後方互換性の維持**
   - 既存の`moon test --native`は引き続き正常に動作する
   - 既存のテストコードへの影響を最小限に抑える

## アプローチ

### 1. 調査フェーズ
- MoonBitのJavaScriptバックエンドのテスト実行方法を確認
- moonbitlang/asyncライブラリのJavaScript対応状況を調査
- Docker APIを呼び出す部分のJavaScript実装可能性を検証

### 2. 設計フェーズ
- バックエンド別のテスト戦略を策定
- 必要に応じたコードのリファクタリング方針を決定
- JavaScriptバックエンドで実行不可能なテストの扱いを決定

### 3. 実装フェーズ
以下の優先順位で実装:
1. JavaScriptバックエンドでのビルド設定追加
2. バックエンド共通のテストコード実装
3. JavaScript固有の実装（必要な場合）
4. テストの分類とドキュメント化

### 4. 検証フェーズ
- 両バックエンドでのテスト実行と結果比較
- CI/CD設定への統合
- パフォーマンスとカバレッジの確認

## スコープ

### 含むこと
- JavaScriptバックエンドでのテスト実行環境構築
- 既存テストのJavaScript対応可能性の評価
- バックエンド別のテスト実行ドキュメント作成
- ビルド設定とCI/CD設定の更新（必要に応じて）

### 含まないこと
- 本番コードのJavaScript最適化（テスト実行が目的）
- ブラウザ専用の機能実装
- Docker操作のJavaScript完全再実装（Docker依存テストはNativeのみとする可能性あり）
- パフォーマンスチューニング（基本動作の確認が優先）

## 影響範囲

### 変更が必要な可能性のあるファイル
- `moon.mod.json`: バックエンド設定追加
- `moon.pkg.json`: テスト実行設定
- `*_wbtest.mbt`, `*_test.mbt`: テストコードの調整（必要に応じて）
- CI/CD設定ファイル（`.github/workflows`など、存在する場合）

### 影響を受けるコンポーネント
- テストインフラ全体
- ビルドプロセス
- 開発ワークフロー
- CI/CDパイプライン

## 技術的な制約と考慮事項

### 1. Docker API呼び出し
- JavaScript環境からDocker APIを呼び出すには、HTTP経由での通信が必要
- Node.js環境では可能だが、ブラウザでは制約がある
- **判断ポイント**: Docker依存テストをJavaScriptで実行するか、Native専用とするか

### 2. Async/Await の実装差異
- moonbitlang/asyncライブラリがJavaScriptバックエンドをどの程度サポートしているか
- イベントループの実装がバックエンド間で異なる可能性

### 3. FFI（Foreign Function Interface）
- Native専用のFFIコールはJavaScriptでは使用不可
- バックエンド別の条件コンパイルが必要になる可能性

## 成功基準

1. **機能要件**
   - `moon test --target js`コマンドが成功する
   - 少なくとも一部のテストがJavaScriptバックエンドで実行される
   - テスト結果が期待通りである

2. **非機能要件**
   - テスト実行時間が許容範囲内（Native版の2倍以内を目安）
   - ドキュメントが更新され、使用方法が明確

3. **品質要件**
   - 既存のNativeバックエンドのテストが全て通る
   - JavaScriptバックエンドで実行不可能なテストが明確に文書化されている
   - コードレビューで品質が確認される

## リスクと緩和策

### リスク1: moonbitlang/asyncのJavaScript非対応
- **確率**: 中
- **影響**: 高
- **緩和策**: 早期に調査を実施し、非対応の場合は代替アプローチを検討

### リスク2: Docker APIのJavaScript実装の複雑性
- **確率**: 高
- **影響**: 中
- **緩和策**: Docker依存テストはNative専用とし、ユニットテスト層のみJavaScript対応

### リスク3: バックエンド間の挙動差異
- **確率**: 中
- **影響**: 中
- **緩和策**: 詳細なテストとドキュメント化、差異を許容する方針を明確化
