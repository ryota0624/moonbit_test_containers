# マルチエージェントシステム

このディレクトリには、Claude Codeでの開発作業を効率化するための5つの専門エージェント定義が含まれています。

## エージェント一覧

### 1. @orchestrator (`orchestrator.md`)
作業全体を統括し、適切なエージェントに作業を委譲する指揮者。

**使用タイミング**: 複雑な開発タスクの開始時

### 2. @software-architect (`software-architect.md`)
技術的な方針を策定し、実装の指針を提供する設計者。

**使用タイミング**: 新機能の技術設計が必要な時

### 3. @test-architect (`test-architect.md`)
動作検証方法を考察・設計するテスト戦略の専門家。

**使用タイミング**: テスト戦略の策定が必要な時

### 4. @coder (`coder.md`)
設計に基づいて実際のコードを実装する実装担当者。

**使用タイミング**: 実装作業を行う時

### 5. @reviewer (`reviewer.md`)
実装コードを設計に沿っているかレビューする品質保証担当者。

**使用タイミング**: 実装完了後のコードレビュー時

## 使用方法

### 基本的なワークフロー

```
ユーザーリクエスト
    ↓
[1] @orchestrator: 作業の解釈と計画
    ↓
[2] @software-architect: 技術設計
    ├─ [3] @test-architect: テスト設計
    ↓
[4] @coder: 実装
    ↓
[5] @reviewer: コードレビュー
    ↓
完了 or 修正へ戻る
```

### Claude Codeでの呼び出し方

各エージェントは、Task toolを使用して呼び出します：

```markdown
# オーケストレータの呼び出し例
Task tool with prompt:
"orchestrator.mdの指示に従って、[タスク内容]を実行してください。"

# 個別エージェントの呼び出し例
Task tool with prompt:
"software-architect.mdの指示に従って、[機能名]の技術設計を行ってください。"
```

### 簡易的な使用方法（小規模タスク）

小規模なタスクでは、必要なエージェントのみを呼び出すことも可能です：

- バグ修正: @orchestrator → @coder → @reviewer
- ドキュメント作成: @coder のみ
- 新機能（小規模）: @orchestrator → @software-architect → @coder

## エージェントの選択ガイドライン

### フルワークフロー（全エージェント使用）
- 新機能の追加
- アーキテクチャの変更
- 広範囲な影響がある作業

### 部分的なワークフロー
**設計不要の場合:**
- @coder → @reviewer
- 例: 明確なバグ修正、タイポ修正

**テスト設計不要の場合:**
- @orchestrator → @software-architect → @coder → @reviewer
- 例: 内部リファクタリング

**レビュー不要の場合:**
- @orchestrator → @coder
- 例: ドキュメント作成、単純な追加

### 単一エージェント使用
- **@orchestrator のみ**: 作業の分析と計画のみ必要な場合
- **@software-architect のみ**: 技術調査のみの場合
- **@test-architect のみ**: テスト戦略の相談のみの場合
- **@coder のみ**: 実装指示が明確な場合
- **@reviewer のみ**: 既存コードのレビューのみの場合

## 各エージェントの主要な責務

| エージェント | 入力 | 出力 | 主要ツール |
|------------|------|------|-----------|
| オーケストレータ | ユーザー要求 | 作業計画、各エージェントへの指示 | Task, AskUserQuestion, Write |
| ソフトウェアアーキテクト | 機能要件 | 技術設計ドキュメント | Read, Glob, Grep, WebSearch |
| テストアーキテクト | 機能要件、技術設計 | テスト設計ドキュメント | Read, Glob, Grep |
| コーダー | 技術設計、テスト設計 | 実装コード、テストコード | Read, Edit, Write, Bash |
| レビュアー | 実装コード、設計ドキュメント | レビューレポート | Read, Grep, Bash |

## ドキュメント管理

### Steeringドキュメント（作業開始前）
`docs/steering/[作業名].md` に作成
- 目的・背景
- ゴール
- アプローチ
- スコープ
- 影響範囲

### 完了ドキュメント（作業完了後）
`docs/completed/[作業名].md` に作成
- 実装内容
- 技術的な決定事項
- 変更ファイル一覧
- テスト
- 今後の課題・改善点
- 参考資料

## ベストプラクティス

### 1. @orchestrator から始める
複雑なタスクは必ず @orchestrator から開始し、全体の計画を立てる。

### 2. 設計を先行させる
コーディングの前に必ず @software-architect による設計を行う。

### 3. テスト戦略を明確にする
重要な機能は、実装前に @test-architect でテスト設計を確定させる。

### 4. レビューを省略しない
重要な変更は必ず @reviewer を通す。

### 5. ドキュメントを残す
Steering → 実装 → 完了ドキュメント のサイクルを守る。

## 注意事項

### エージェント間の情報共有
- 各エージェントは前のエージェントの成果物を必ず参照する
- @software-architect の設計を無視した実装は禁止
- @reviewer は設計ドキュメントを基準にレビューを行う

### 独断での変更禁止
- @coder は設計からの独断での逸脱禁止
- 問題を発見した場合は @orchestrator に報告

### スコープの厳守
- 要求された範囲のみを実装
- 「ついでの改善」は避ける

### 品質基準の維持
- セキュリティの確保
- テストの実装
- コード品質の維持

## トラブルシューティング

### 設計と実装が合わない
→ @orchestrator に報告し、@software-architect と調整

### テストケースが不明確
→ @orchestrator に報告し、@test-architect と調整

### レビューで多数の指摘
→ @coder に修正依頼、必要に応じて設計を見直し

### エージェント定義が不適切
→ このREADMEおよび各エージェント定義を更新
